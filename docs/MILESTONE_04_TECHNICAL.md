# 第四里程碑技术探索与证据

本记录覆盖第三里程碑之后至 2026-11-02（UTC）的回复延迟排查、方案选择和部署验证。成果摘要见 [第四里程碑](MILESTONE_04.md)。原第三里程碑及更早记录保留历史口径。

## 1. 问题最初表现为“收到了，但没有回”

文字和媒体基础链路已经可用后，实际使用暴露出两个不同的问题：

1. **回复渠道偏移**：多条事件合并后的任务提示可能把确认留在原助手界面，没有回到微信。
2. **处理启动延迟**：消息已经进入桥接 pending，请求内容完整，但自动通知数分钟后才交到助手。

前者涉及处理指令与回复目的地；后者涉及消息何时被执行任务读取。修改回复渠道规则可以减少回错位置，却不能让一条尚未交到会话的通知提前到达。因此排查将这两个问题分开，不再用一个笼统的“桥接失败”覆盖整条链路。

在渠道处理上，保留原请求和发送结果，按来源回复。已在微信 accepted、sending 或 unknown 的同次发送不补发；迟到事件只用于核对处理状态。这些规则沿用已有幂等机制，没有增加一套审核或消息拦截流程。

## 2. 先确认请求在哪里，再判断哪一段慢

### 2.1 初次读取能够确认的事实

通过已有工具读取 pending、连接状态、订阅数和回调诊断，可以看到：

- 本人消息已进入待处理列表，正文可直接读取；
- 微信通道连接正常，原订阅仍在；
- 回调诊断显示 HTTP 200 / accepted；
- 助手尚未开始处理对应请求。

这一步排除了“消息根本没有进入桥接”的假设，但还不能精确归因。`test_status` 的回调诊断是**最新一次状态快照**，没有在返回结果中给出对应事件及完整时间线。不能把一个成功快照当作每条消息都及时投递的证据。

### 2.2 复核自己的代码，而不是直接归责平台

随后检查实际通知调度路径：

- 运行循环分别调度微信收件和事件投递；
- 新事件的首次尝试时间设为当前时刻，没有正常路径固定等待五分钟的逻辑；
- 投递网络调用有超时；失败后按约 `1、2、4、8、16、32、60` 秒退避，之后继续按上限重试；
- 事件投递串行执行，失败重试或前项等待确实可能累计成多分钟。

因此，“桥接有成功状态”仍不足以排除桥接自身退避。所需证据是**具体事件尝试了几次、何时发出、何时收到成功响应**。

### 2.3 利用已有字段取得逐事件证据

第三里程碑已有的事件记录包含以下字段：

| 字段 | 用途 |
| --- | --- |
| `attempts` | 判断是否经过重试 |
| `dispatchStartedAt` | 最后一次投递开始时间 |
| `httpCompletedAt` | 最后一次 HTTP 调用完成时间 |
| `httpStatus` | 投递响应状态 |
| `errorCode` | 固定错误分类 |
| `status` | 当前事件投递状态 |

本次只读提取指定事件的这些元数据，与助手实际收到通知的时间对应。没有新增全量日志，也没有导出聊天正文、完整加密状态或凭据。

这组字段保留最后一次尝试及累计次数，不提供每次失败的完整历史。但在 `attempts=1` 时，它足以确定首次成功投递的时间。

## 3. 三条事件把长等待定位到受理之后

以下使用匿名样本及相对时长，不公开原始事件标识和精确活动时间。

| 样本 | 收件→开始投递 | 收件→HTTP 完成 | HTTP 完成→助手收到通知 | 尝试与结果 |
| --- | ---: | ---: | ---: | --- |
| A | 0.173 秒 | 2.728 秒 | 5 分 9.573 秒 | 1 次，200，accepted，无错误 |
| B | 0.088 秒 | 3.011 秒 | 5 分 11.241 秒 | 1 次，200，accepted，无错误 |
| C | 0.135 秒 | 2.691 秒 | 12 分 57.867 秒 | 1 次，200，accepted，无错误 |

这三条证据明确了两点：

- 桥接收件后很快开始通知，且首次投递成功，长等待不是这三条消息的退避重试造成的。
- 数分钟等待发生在平台接受回调之后。平台内部究竟是排队、聚合还是会话唤醒，需要对应服务端调度记录进一步区分。

[MCP Events 官方说明](https://developers.openai.com/plugins/build/mcp-events)将成功响应与后续异步处理分开；[任务说明](https://learn.chatgpt.com/docs/automations)也提及邻近事件可能合并。两份说明都不能推出“每条消息固定等五分钟”。本次出现约十三分钟的样本，也不支持固定五分钟结论。

## 4. 走过哪些方案，为什么没有停在这些方案上

| 方案 | 实际检查结果 | 取舍 |
| --- | --- | --- |
| 修改消息来源与回复渠道规则 | 可明确微信来源应回微信，不能改变通知到达时间 | 保留必要规则，单独解决处理延迟 |
| 缩短微信收件长轮询的约 35 秒等待 | 这是无消息时的最长等待；有消息可提前返回，发送使用独立路径 | 不改。数分钟延迟发生在收件并成功投递之后 |
| 关闭批处理或提高任务优先级 | 现有任务编辑、高级设置与工具参数未暴露相应选项 | 没有凭空添加配置，也没有重建重复订阅 |
| 对 webhook 任务调用“立即运行” | 当前任务入口不可用，相关立即运行能力不等于 webhook 的低延迟入口 | 不作为实时链路 |
| 改用 Workspace Agent trigger API | 对应已发布的另一类 Agent，需要其访问凭据，仍有异步入队 | 不替换当前私人会话或增加第二个模型入口 |
| 等待平台反馈 | 技术时间线和逐事件证据已经提交，但无可用处理时限 | 继续跟进，同时实现不依赖通知及时性的处理方式 |
| 当前会话短间隔查询 pending | 能直接取到已到请求，迅速接续积压 | 作为临时接续，再改为低空转的直接等待 |
| 给现有 pending 接口增加长等待 | 可以复用已验证的本人消息队列和原处理语义 | 选为本阶段实际落地方案 |

Workspace Agent 接口的范围见[官方触发说明](https://developers.openai.com/workspace-agents/trigger-runs)。它不是当前私人 dot 的即刻注入入口。方案选择始终围绕“保留同一会话、沿用现有身份和状态、减少无效等待”。

## 5. 最小接口改动

部署实现扩展原 `list_pending_owner_requests`。运行侧改动集中在 relay 模块，使用内存新请求通知与单次截止 timeout 完成等待：

```json
{
  "wait_ms": 20000
}
```

| 参数或行为 | 约定 |
| --- | --- |
| `wait_ms` | 可选，整数毫秒，范围 `0–20000` |
| 省略或 `0` | 与原接口一致，立即返回当前 pending |
| 队列已有请求 | 立即返回，不等待满指定时间 |
| 空队列 | 等待新请求或截止时间，哪个先到就返回 |
| 返回值 | 沿用原请求列表、正文完整标记和附件元数据 |
| 处理状态 | 仍由原回复／handled 工具更新，不因读取自动完成 |

客户端运行方式：

```text
开始一次 pending 等待
  ├─ 有请求：合并理解相关消息 → 按需取附件 → 回复 → 再次等待
  ├─ 空结果：再次等待
  └─ 工具异常：检查并恢复收件；不重放结果不明的发送
```

这是服务端等待新请求，不是在客户端每二十秒放行一批消息。等待上限控制单次工具调用时长，新消息会提前结束等待。

## 6. 并发、锁与兼容要求

新等待逻辑必须满足的不是“能等二十秒”，而是“等的时候收件与发送还在工作”。实现和测试围绕以下约束展开：

1. **不在共享服务锁内长等**：短暂读取 pending 状态后释放共享执行路径，在外部等待新请求或截止。
2. **单个持续等待**：一个活跃主任务只维持一个 pending 等待，避免重复占用 MCP 并发槽。
3. **保留其他工具的并发空间**：现有媒体并发配置保持，等待不能占满发送和附件处理能力。
4. **兼容旧调用**：默认 `wait_ms=0`；原请求结构、handled 和幂等键不迁移。
5. **保留事件订阅**：主动等待不是第二套消息存储；两条路径读取同一请求状态，晚到事件不会触发重复回复。
6. **不增加常驻周期任务**：一次调用的截止等待属于接口本身，不新建问候定时器、轮询自动化或后台内容分析。

正常回复仍使用真实请求标识和每次发送的稳定幂等键。不同进度、补充和最终回复可以使用不同键，同一次发送保持原键。`accepted`、`sending`、`unknown` 的历史结果继续保留。

## 7. 部署与验证过程

### 7.1 本地实现验证

本轮相关测试共 **69 项通过**，覆盖默认立即返回、新消息唤醒、空队列超时，以及等待期间读取和回复可执行等行为，随后按既有部署方式加载新实现。原账号绑定、加密状态和订阅保留，没有重新扫码或创建新 webhook。该数字对应本轮定向测试，不与此前版本的测试数量相加。

### 7.2 刷新原插件工具

在原插件设置中执行“刷新工具”，然后用实际宿主调用验证参数行为。检查时曾出现工具描述仍显示旧无参形式、实际调用已接受 `wait_ms` 的情况；是否生效以受支持的刷新结果和真实调用行为共同确认，没有通过正文伪造工具参数。

### 7.3 空等待与并发验证

两次空队列请求分别约 **20.762 秒、20.670 秒**返回，均为空结果。另一次等待开始后，在第 1 秒发起状态读取，该读取约 **2.509 秒**完成，早于 pending 等待结束。

这项验证证明长等待没有堵住并发状态调用。实际回复发送另由随后自然聊天验证，不把“状态读取可并发”直接等同于全部发送测试。

### 7.4 自然文字与空闲后首条消息

主任务接管单个持续等待后，第一条自然文字从桥接收到到助手拿到请求约 **2.1 秒**。随后多条真实回复成功返回 accepted，其中两次回复工具调用约 **2.6 秒、3.3 秒**。

持续空闲二十余分钟后，下一条自然文字仍在约 **2.2 秒**内被读取，回复工具约 **4.2 秒**完成。该结果验证了等待覆盖空闲期间的新消息，而不只是处理已经存在的积压。

另有一次回复工具耗时约三十余秒，最终 accepted；该次缺少完整阶段时间，未归因于长轮询。它提示收件提速与整次回复耗时是不同指标，后者还包含执行、工具发送和网络过程。

### 7.5 真实图片往返

图片到达后约 **2.6 秒**取得请求，随后按真实附件引用读取图片，理解并发送回复；用户确认约**二十多秒**收到回复。公开记录不包含图片本身、文件名、请求标识或聊天内容。

这次自然图片测试把第三里程碑的媒体能力与新收件路径连在一起，验证了“长等待中图片来信→原图读取→同一会话回答→微信回复”。

## 8. 如何正确理解这次提速

本阶段使用四个不同时间点描述链路：

```text
T0 桥接保存来信
T1 webhook HTTP 调用完成
T2 助手取得请求并可以处理
T3 回复工具返回 accepted
另：用户实际看到回复的时间
```

旧路径主要检查 `T1→T2`，新路径主要检查 `T0→T2`。图片的用户观察覆盖更多步骤。不能将一个约 2 秒的收件指标写成所有文字、文件都保证 2 秒回复，也不能将发送 accepted 直接写成手机已显示。

本次直接等待消除了**活跃任务对及时 webhook 调度的依赖**。主任务停止后，直接等待也会停止；原事件订阅负责后续通知。平台调度本身未因这次桥接改动被修复，保留它与新路径可以兼顾接续与即时处理。
