# 第四里程碑：直接等待收件，消除活跃会话的通知等待

记录日期：2026-11-02（UTC）。上一里程碑：[第三里程碑 · 0.3.0 文字／图片／文件完整版](MILESTONE_03.md)。

## 1. 这次解决了什么

第三里程碑解决了“文字、图片、文件能否交给同一个助手处理”。本阶段继续解决日常使用中的关键问题：**桥接已经收到消息，助手却迟迟没有开始回答。**

逐事件记录显示，三次通知都在约 3 秒内首次投递成功，平台返回 HTTP 200；通知真正交到会话处理前，又等待约 5 分钟、5 分钟和 13 分钟。调整微信收件轮询时间无法减少这段等待。

第四里程碑将活跃会话的收件方式改为**直接等待 pending 请求**：有消息时立即返回给当前助手，队列为空时最多等待 20 秒，再继续等待。原 webhook 保留，晚到事件按原请求去重。回答仍由同一个助手完成，桥接没有增加额外模型。

**本次成果是把平台通知调度从活跃会话的实时处理关键路径中移出。** 新路径已经部署并通过真实文字、图片往返；平台自身的异步调度问题仍单独跟进。

## 2. 从第三里程碑到第四里程碑

| 第三里程碑已有能力 | 本阶段新增与完善 |
| --- | --- |
| 活跃会话可主动查询 pending，接续已到消息 | 查询接口增加可选 `wait_ms`，空队列时直接等待新消息，形成连续收件路径 |
| 文字、图片、文件以及引用进入同一会话 | 保持原内容读取与回复能力，不另建机器人或会话 |
| Events 通知、晚到去重 | 保留订阅作为通知路径，与主动等待共用请求状态 |
| 每次发送独立幂等、显式 handled | 沿用原语义，主动读取与晚到事件不会重复发送 |
| 回调记录已有发送起止、HTTP 状态等字段 | 按单条事件关联阶段时间，区分桥接投递与平台调度耗时 |
| 媒体模式并发与连接复用 | 验证等待不占住共享服务锁，其他工具仍可并发执行 |

“主动查询 pending”不是本阶段首次出现。此次变化是从**处理后顺手查一次**，发展为**会话持续直接等待新消息**，并完成接口、部署及真实交互验证。

## 3. 架构变化

### 原来的通知依赖路径

```text
微信消息
  → 桥接收件并保存请求
  → webhook 投递并获 HTTP 200
  → 平台异步调度
  → 助手开始处理
  → 原回复接口
  → 微信
```

### 第四里程碑的活跃收件路径

```text
微信消息 → 桥接收件并保存请求 ─→ 原 webhook 订阅（保留）
                    │                    │
                    │                    └→ 晚到事件按请求去重
                    ↓
        list_pending_owner_requests(wait_ms=20000)
                    ↓ 有消息即返回
               同一助手处理
                    ↓
               原回复接口 → 微信
```

等待发生在桥接侧的待处理请求接口。20 秒是空队列等待的上限，不是每条消息必须等待的时间。

## 4. 实测结果

| 测量项 | 观察结果 | 表示什么 |
| --- | --- | --- |
| 旧路径，三条通知的首次投递 | 全部一次成功，约 3 秒内获 HTTP 200 | 桥接没有重试或多分钟发送积压 |
| 旧路径，HTTP 受理后到会话收到通知 | 约 5 分 10 秒、5 分 11 秒、12 分 58 秒 | 长等待发生在平台受理之后 |
| 新接口空队列等待 | 20.762 秒、20.670 秒返回 | 等待上限在真实宿主生效 |
| 等待期间并发状态读取 | 2.509 秒完成，早于等待结束 | 等待没有堵住其他状态调用 |
| 新路径自然文字来信 | 桥接收件到助手取得请求约 2.1 秒 | 不再等待数分钟的通知投递 |
| 持续空闲二十余分钟后的新文字 | 收件到取得请求仍约 2.2 秒 | 连续等待覆盖了空闲后首条消息 |
| 新路径真实图片 | 用户确认约二十多秒收到回复 | 包含收件、图片读取、理解及回复的用户侧观察 |

这些数值来自不同阶段，不能互相替代：约 2 秒是**收件到取得请求**；图片二十多秒是**用户观察的整次交互**。详细口径、实现与探索过程见 [技术探索与证据](MILESTONE_04_TECHNICAL.md)。

## 5. 实现与验收

- `list_pending_owner_requests` 增加可选 `wait_ms`，范围 `0–20000` 毫秒，默认 `0`，旧调用仍立即返回。
- 单个活跃会话只保留一个等待调用，收到消息后沿原请求、附件与回复接口处理。
- 等待逻辑不持续持有共享服务锁，不阻塞微信收件、回复或其他 MCP 调用。
- 本轮相关测试 **69 项通过**；沿原部署方式更新并刷新原插件工具。
- 原绑定、凭据、状态、订阅和回复幂等记录保留，没有创建第二套自动化。
- 真实文字已跑通“等待中来信→返回请求→回复 accepted”，真实图片得到用户侧回复确认。

## 6. 使用方式与运行条件

本方案用于**正在运行、能够持续调用工具的同一助手任务**。任务收到请求后处理并回复，再进入下一次等待；空队列继续等待。若主任务停止执行，后续唤醒仍依赖保留的事件通知，不能把直接等待写成独立的永久唤醒服务。

持续收件使用已有连接和一个等待槽，不额外设置问候任务、周期自动化或新的账号。断线、工具异常和宿主调度仍需按实际错误处理。平台回调受理后的调度问题已提交技术反馈，本文不把反馈提交当作平台修复完成。
