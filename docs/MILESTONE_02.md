范围：2026-10-28 阶段一发布之后到 17:03 UTC 的正式版里程碑。本文从已执行的变更与验收重构，不包含原始聊天、日志、账户标识或机器配置。测试数字对应当时修订，不相加冒充最终全量结果。

本文保留第二里程碑当时的能力与未完成事项；第三里程碑的文字／图片／文件完整版见 [MILESTONE_03](MILESTONE_03.md)，本阶段详细证据见 [历史证据归档](MILESTONE_02_EVIDENCE.md)。

## 1. 长轮询卡住与实际连接池恢复

控制面请求会停在 wait_response，已观察到 HTTP/2 与复用连接。设备列表显示 connected 并不能证明工具请求已执行成功；执行器断连与桥接控制面超时分别记录，不能互相解释。

第一版 .1 设连续三次自身 poll deadline 才更换池。离线测试通过后，真机出现五次 timeout、connection_pool_resets 仍为零，证明真实错误分类被漏掉。后续修复对齐 http.Client.Timeout、poll context deadline 及包装错误，仍排除父 context 取消和正常空 longpoll。未把阶段 wait_response 本身宣称为网络根因。

.2 真机在 11:32–11:33 UTC 换池后，get 与 reply 恢复成功。后来继续观察到恢复。这证明更新底层连接池能恢复实际故障，不意味着解释了所有网络异常。代理、TLS 身份校验与未知发送不重放保持不变。

.3 保持 10 秒 longpoll + 30 秒 deadline guardrail，只把门槛降到第一次自身 deadline。三次门槛理论额外等待约 80 秒；这是参数推算，不能写成每次实测精确节省。官方 poll 返回空结果不触发重建；偶发真超时的代价是下一次连接建立。补丁包含实际 TCP 池更换、父取消、正常空返回和在途不重放测试。

## 2. 先解决大耗时，再删工具往返

配对时间证据见性能页：本机到平台事件通常约 2–2.5 秒，后续平台投递、合批或根会话排队曾达 61–114 秒。不能把这整段称为纯平台唤醒；根会话也可能正在处理其他消息。

活跃执行脚本查询真实 pending 能更早发现消息。正常事件带真实 ID 时直接 get，取消无必要 list。随后 Events 和 pending 在输入 schema 不变的前提下加入 text/text_complete；完整短文字直接处理，省掉一跳实测 4–9 秒的 get。超预算保持完整原文可读取，不伪造 request_id 或引入特殊 next 值。

考虑过合并 list/get、改长轮询参数和微调 250ms 调度，但优先选择有绝对秒数收益的真实路径。没有为不足一秒的计时器改动重启。本人鉴权和形态校验没有证据显示为主要 CPU 瓶颈，没有为提速删除这些检查。

## 3. 主动读取优先，通知兜底

正文直达后仍有晚到的批量 Events 插入会话，某次处理与调度段达到 34 秒；它与通知插入同现，但不能全归因于通知。实现近期成功读取时的有界延迟，只在 reply accepted 后取消未发出的通知。

先前一轮三次测试没有晚到事件，但当时迁移后 callback 订阅尚未恢复。因此这些数据只能证明主动路径，不算通知协调成功。补恢复原唯一订阅后再继续观察；这一纠正保留，避免用缺失订阅制造性能成绩。

没有伪造保活事件、永久关掉订阅或另建通知服务。已经被平台接受的事件不能撤回，晚到去重仍是必需。

## 4. 后台隐藏、二维码和空白窗口

隐藏日志宿主后，displayed_locally 回执曾报告显示，但用户没看到二维码。改为独立 WinForms 窗口，显式显示、恢复、置前并核实可见性；图片仅留内存。正常后台与一次扫码显示分离。

后来空白 Windows Terminal 持续存在。最初只证实收发进程与 Terminal 的控制台/父子关系不同，就推断关闭不影响后台，遗漏了监督进程。窗口消失后收发仍在，但监督任务已退出，结果码 0xC000013A 表示控制台中断。没有充分证据断言具体哪次窗口操作触发中断。

修正为原计划任务以 wscript 无控制台入口启动隐藏监督器，桥接子进程使用 CreateNoWindow。实际加载后任务 Running、监督及桥接进程存在且未发现 Windows Terminal。没有关闭无关终端，没有新增管理员服务或托盘框架。

## 5. 从定时试验转为正式运行

试验先从短时扩大到 12 小时，并保持同一轮绝对截止，重启不能重置。用户随后批准长期模式、当前用户登录启动、加密保存登录与未完成状态。正式模式才取消试验硬截止；QR 有效期、真正请求超时和服务端授权时效没有被伪造成无限。

已有专用隧道密钥在官方控制台支持直接改为 Never，沿用原密钥和 read/use 范围，无需创建或在聊天中交接新 secret。本地到期元数据在服务端确认后同步；修改本地日期不等于服务端延期。公共源码只支持使用者录入真实官方期限。

引入 DPAPI 包装随机数据密钥，状态 AES-GCM 原子保存。发送先记录意图；中途崩溃按 unknown 恢复，不重发。成功回复与引用正文的保留分开；处理完成不再立即抹掉仍有引用用途的正文。

计划任务最初无法找到已保存凭据，原因是打包应用的 LocalAppData 虚拟视图与任务看到的物理路径不同。修复为指向原存储位置，没有搬运凭据。公开版使用通用 LocalAppData 目录，去除原机器打包路径。部署时必须使用同一 Windows 用户和同一明确存储目录。

真实交接验证了正常停止、由原任务接管、免扫码恢复本人绑定、原 callback / 订阅数量保持 1、重启前 pending 在恢复后被读取和回复。清理曾因空 AppData/Roaming 子目录残留报告未确认；修复只删除已知空目录，未知文件不会递归删除。

## 6. 引用解析与真机闭环

第一轮 quoted 返回 not_cached，不能猜引用的是哪条。排查发现：成功后清正文会丢缓存；svr_id 被不必要地限定为 uint64；partial_text 实际是对象；引用项 type 为可选字段。这些分别修复，但后续真实消息仍缺来源 ID，证明缓存容量不是根因。

再核官方 inbound.ts，发现外层 svr_id 缺失时应取内层 message_item.msg_id。补此路径并增加仅已验证本人消息的结构诊断：固定字段名、类型、存在性、计数，无字段值、原文、ID 或未知键名。正常空轮询不会清掉最近一份诊断；重启清除。

16:47 UTC 真机引用在 cached 状态下匹配到上一条出站回复原文，根据原文回答并获得 accepted。这是实际引用成功，不是合成测试或根据聊天猜测。出站 message_id 仍是可选字段；未提供 ID 的出站消息不能做精确 ID 引用匹配。没有承诺原生微信出站引用泡泡。
