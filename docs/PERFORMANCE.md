# 性能与证据

## 第四里程碑：活跃会话直接等待

三条实际事件均首次投递成功，收件到 HTTP 200 完成约 2.7–3.0 秒；平台受理到会话收到通知仍分别等待约 5 分 10 秒、5 分 11 秒、12 分 58 秒。与早期状态快照不同，本次按单条事件的 attempts、dispatchStartedAt、httpCompletedAt 和状态交叉核对，可排除这三例由桥接退避导致的数分钟等待。

部署中新增 pending 的可选 wait_ms，活跃任务直接等新消息。两次空队列调用约 20.762／20.670 秒返回，并发状态调用在等待结束前约 2.509 秒完成。自然文字收件到取得请求约 2.1 秒；持续空闲二十余分钟后的新来信约 2.2 秒。图片用户观察约二十多秒收到回复。

约 2 秒是取得请求的耗时，不是所有回复的总时长；平台异步调度仍独立存在。精确口径、方案筛选和持续运行条件见 [第四里程碑技术记录](MILESTONE_04_TECHNICAL.md)。本次文档发布未更新仓库源码。

## 第三里程碑历史记录

0.2.0 的完整历史记录见 [历史证据归档](MILESTONE_02_EVIDENCE.md)；下文记录本版本状态。

0.3 删除 pending 达 100 条后停止接收的自设门槛；空轮询游标不变、重复 handled 不再保存。单请求读取避免复制整个状态，replace 减少重复 clone。全量加密快照仍存在，不能宣称已完全消除同步 IO。

HTTP Agent 复用空闲 CONNECT/TLS 连接，不增加网络调用。合成传输测试确认连续两次完成调用只创建一次 CONNECT 和 TLS。文字长轮询与发送不共享单槽连接。媒体模式 tunnel/MCP 并发 4，附件准备两份并行；缓存命中避免重新下载和上传。

webhook dispatchStartedAt/httpCompletedAt/httpStatus/errorCode 与发送 startedAt/finishedAt 写入原记录，不新增落盘步骤。没有新增计时轮询、额外模型调用或内容扫描。

私有部署此前三条文字从本地接收到准备 webhook 约 0.16、0.26、0.16 秒；父会话开始处理分别晚约 16 秒、126 秒、19 秒。旧数据缺少 HTTP 接受精确时间，不能据此把等待全部归因于某一层。旧普通图／小 PDF 回传工具耗时约 10.1／12.2 秒，不代表新版本速度。

0.3 尚未通过自然交互测出完整端到端收益。连接复用测试、独立文字执行测试只能证明对应代码行为，不证明平台唤醒时间下降。
